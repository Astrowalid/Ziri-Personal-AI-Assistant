# v3 Documentation: Long-Term Memory

This document details the planning, scope, and technical design for the third version (v3) of the Personal Assistant Agent. It serves as the specification and source of truth for the v3 implementation.

---

## 1. Goal / What This Version Proves

v3 introduces long-term memory to the Personal Assistant Agent. It transitions the agent from a session-only notifier into an assistant with a track record. It proves:
* The capability of the agent to persist the planned-vs-done state of tasks and events across multiple days and bot restarts.
* The ability to adjust daily check-ins dynamically (e.g., asking "did you finish X?" instead of just announcing due dates).
* Integration of Google's Agent Development Kit (ADK) Session/Memory concepts, or an equivalent persistence layer, alongside active Calendar and Classroom APIs.

---

## 2. Done Criteria (Scope)

The implementation of v3 is considered complete when the following criteria are met:
* **Accurate Completion Queries**: The agent can accurately answer questions like *"what did I finish this week?"* using real persisted historical data, rather than live recomputation from the Calendar/Classroom APIs each time.
* **Persistent Status Tracking**: The status of assignments and calendar events is stored persistently across bot restarts, not just within a single running session.
* **Context-Aware Check-ins**: Daily check-ins reference yesterday's or this week's actual completion history, rather than presenting only today's live Calendar/Classroom state.
* **7-Day Validation**: The system is successfully tested across at least 7 real days, showing accurate memory of what was and was not completed.

---

## 3. Explicitly Out of Scope

To keep the scope focused and achievable, the following are explicitly excluded from v3:
* **Writing Status to Google Calendar/Classroom**: The agent does not modify status fields, marks, or event details back in Google Calendar or Google Classroom. Status lives exclusively in the assistant's own persistent store.
* **Gmail / Email Integration**: Reading or drafting emails remains out of scope (planned for v4 and v5).
* **Weekly Planning Conversation UX**: A structured Sunday weekly planning flow is out of scope (planned for v6, which will build upon this persistence layer).

---

## 4. Technical Design & Architecture

### Architecture Note
v3 is the first version requiring persisted storage. The Google Calendar and Classroom tools remain read/write as they are now; v3 adds a new persistence layer alongside them without changing their fundamental behavior.

### Storage Choice: SQLite (`sqlite3` Standard Library)
* **Decision**: Use Python's built-in `sqlite3` module for local storage.
* **Rationale**:
  * **vs. Local JSON**: JSON lacks structured query capabilities; querying completion history over arbitrary date ranges (e.g., *"what did I finish this week?"*) would require loading all records into memory and custom filtering in Python.
  * **vs. ADK Session/Memory Services**: ADK's built-in memory services are designed primarily for cross-conversation semantic recall and conversational history, not structured relational status queries. SQLite is straightforward to inspect, migrate, and test independently of the agent runtime.
* **Deployment Note**: Future hosting (e.g. Oracle cloud VM in v7) does not alter this decision. SQLite operates as a single file on local disk alongside the process. Since v3 is single-user and single-process, concurrency and locking are non-issues.

---

## 5. Data Model & Status Logic

### 1. Task Status Model
* **Decision**: Three-State Status Model:
  * `NOT_STARTED`: The task/assignment exists on the schedule but work has not begun.
  * `IN_PROGRESS`: The user has indicated they are actively working on the task.
  * `DONE`: The task has been completed.
* **Rationale**: Three states accurately capture active student workflows without overcomplicating transition logic. The 4th state (`SKIPPED`) is deferred to v6 (Weekly Planning) as it directly couples with the weekly planning agenda and postponements.

### 2. Unique ID Mapping & Schema Separation
* **Decision**: Composite primary key `(source_type, source_id)`:
  * `source_type`: String enum (`'calendar'` | `'classroom'`).
  * `source_id`: String storing the verbatim `event_id` (Google Calendar) or `courseWork_id` (Google Classroom).
* **Rationale**:
  * Avoids synthesized single-string keys, keeping Google Calendar and Google Classroom data cleanly separated in the schema per v2 design principles.
  * **ID Stability**: Both Google Calendar `event_id` and Google Classroom `courseWork_id` are immutable across updates and edits (Google's patch/update endpoints target the ID in the URL; the ID itself cannot be modified). An ID only changes if an item is deleted and recreated, which manifests as `NOT_FOUND` on subsequent API fetches rather than silent data drift.

### 3. Reconciliation Strategy: Classroom-Dominant
* **Decision**: Option A (Classroom-Dominant with user warning).
* **Rationale**: Google Classroom's live submission status serves as the definitive source of truth. If a discrepancy occurs between the assistant's local database and Classroom (e.g., the user marked a task `DONE` in chat, but the live Classroom API indicates `not-submitted`), the agent warns the user during check-in rather than silently trusting either state or overwriting records without prompt.

## 8. Resolved Decisions

1. **Persistence Mechanism**: Standard library `sqlite3` chosen over JSON (query limitations) and ADK Session/Memory Service (semantic rather than structured status tracking).
2. **Status State Model**: Three-state (`NOT_STARTED`, `IN_PROGRESS`, `DONE`). `SKIPPED` deferred to v6.
3. **Reconciliation Strategy**: Option A (Classroom-Dominant). Discrepancies prompt a user warning rather than silent synchronization.
4. **Unique ID Mapping**: Composite key `(source_type, source_id)` maintaining explicit separation between Calendar and Classroom domains with confirmed immutable Google resource IDs.
